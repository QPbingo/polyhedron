# Native CLI compatibility

Checked installed CLI help on 2026-09-08: Codex `0.153.4` (`/opt/homebrew/bin/codex`), Claude Code `2.1.236` (`/opt/homebrew/bin/claude`). Minimum capability gates are those versions, within their current major line. Later minor versions are probed for configuration flags but still require release smoke testing. No model prompt, login, global vendor configuration edit, permission bypass, hook trust bypass, or real history resume was performed.

`detectAgents(): Promise<AgentInfo[]>` reports paths, versions, launch availability, and hook capability. `hooks: true` means this version supports the configured interface, not that native hook trust has been granted. Missing or unsupported binaries produce a reason and cannot be launched.

`buildLaunch({ agent, cwd, nativeSessionId?, sessionId, runtimeToken, hookToken, hookSocket, dataDir })` returns `{ file, args, env }`. The host must merge the returned **environment overrides** into its sanitized native process environment and launch a PTY with `cwd`; the adapter never spawns the interactive session. `runtimeToken` is a random in-memory Hook correlation secret, not an ordering counter. Codex uses `--cd`; Claude uses the PTY cwd. Every resume includes the exact captured UUID (`codex resume UUID`, `claude --resume UUID`); no recent-history selector or transcript guessing is used.

Codex command hooks are injected per invocation with `-c hooks.Event=[{hooks=[...]}]`. Codex treats CLI values as a separate SessionFlags layer and discovers hooks from each active layer additively, so matching user/project inline hooks and hooks.json files remain present. This is hook-specific discovery, not the ordinary effective-config array replacement rule. Codex may request native hook trust for this source, and this application does not pre-trust it or bypass trust. Claude receives `--settings` with a JSON hooks object, merged by the native CLI with its settings. Native project trust, login, and approval prompts remain visible and actionable in the terminal. See [Codex hooks](https://learn.chatgpt.com/docs/hooks) and [Claude hooks](https://code.claude.com/docs/en/hooks).

The command invokes `process.execPath` with the absolute standalone `backend/scripts/hook-bridge.mjs`, correctly shell-quoting both paths. The same relative layout works from source (`src/adapters`) and build (`dist/adapters`), with no TypeScript loader or post-build copy required. Ship `scripts/` together with `dist/`.

The bridge receives raw native input only in memory, caps it at 256 KiB, and posts to Unix HTTP `/hook` using the per-runtime Bearer token from environment. It emits no stdout/stderr and exits zero on failure. A 1.5-second whole-process timer and native 2-second timeout bound stalled stdin or IPC. It sends only `{ sessionId, runtimeToken, event, nativeSessionId?, eventId, agentId?, toolUseId?, toolName?, at }`; `at` is ISO time. It preserves a valid vendor event ID, otherwise creates a random UUID (there is no reliable cross-invocation deduplication when the vendor supplies no ID). Prompt, tool input/output, approval reason, transcript path, and model response are discarded. Tool names use the same bounded identifier allowlist and allow conservative correlation when native PermissionRequest omits tool_use_id. Tool arguments remain excluded. Child identifiers are retained, and malformed child identifiers drop the event rather than becoming parent activity.

Allowed status events: SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, Stop, SessionEnd; Claude additionally registers PostToolUseFailure. Hooks only observe; they cannot approve, deny, inject context, or keep an agent running. Stop is turn completion, not PTY exit. The host must ignore child events for parent activity, capture native IDs only from parent SessionStart, deduplicate event IDs, authenticate token/runtime, and treat missing hooks as unknown activity. No terminal-text parsing should invent a trusted approval state.

Local verification uses fake CLI version/help binaries and real Unix-socket hook traffic, including redaction, unsafe events, exact UUID resume, missing binaries, unsupported versions, silent failure, and stalled stdin. Real native hook trust/delivery, paid turns, permission prompts, history resume, and Keychain access remain manual acceptance checks with the user's native account. `npm run diagnose` is safe to run without those checks.

Approval correlation prefers exact toolUseId. Where native PermissionRequest omits an ID, a matching safe toolName can identify subsequent tool activity; a differently named parallel tool must not clear it. When neither ID nor tool name is present, keep approval unresolved until an authoritative Stop/SessionEnd rather than guessing. Multiple same-named parallel requests without IDs remain inherently ambiguous; the host should resolve conservatively.


## Verified hook composition in Codex 0.153.4

The official [hook discovery documentation](https://learn.chatgpt.com/docs/hooks#where-codex-looks-for-hooks) describes additive matching hooks across active config sources. The exact installed release is also source-verifiable: the [0.153.4 config loader](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/config/src/loader/mod.rs#L419) appends CLI overrides as a distinct SessionFlags layer; [0.153.4 hook discovery](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/hooks/src/engine/discovery.rs#L119) iterates all active layers, parses each layer's own hooks value, and appends its handlers. Session hooks have the separate synthetic source `/<session-flags>/config.toml`. Thus the adapter's per-session hook arrays do not replace user/project hook arrays. Native hook trust, disabled hooks, and managed-only requirements still govern whether any individual handler runs. The adapter never changes those policies or claims successful hook delivery from version detection alone.
